# Openrooms

Openrooms is an open-source first-person 3D exploration game built with
Godot 4 and GDScript.

The game is inspired by the architectural and liminal atmosphere of the
Backrooms, but it should evolve as its own project.

## Current development stage

The project is currently at the prototype stage.

The initial goal is deliberately small:

- create a first-person player controller;
- create a simple maze-like 3D environment;
- allow the player to explore the environment;
- implement dynamic ceiling lights;
- give the player a flashlight;
- establish the basic visual and atmospheric style.

Do not add enemies, entities, inventory systems, objectives, procedural
generation, save systems, or other major gameplay systems unless explicitly
requested.

Avoid overengineering the prototype.

## Technology

- Engine: Godot 4.x
- Language: GDScript
- Platform: Linux is the primary development platform.
- Prefer standard Godot functionality over third-party addons.
- Prefer typed GDScript when it improves clarity.
- Do not introduce C#, GDExtension, or external dependencies unless explicitly
  requested.

## Project organization

Use this general structure:

- `scenes/` - Godot scenes
- `scripts/` - GDScript source code
- `materials/` - reusable Godot materials
- `assets/` - textures, sounds, models, and other imported assets
- `docs/` - design and technical documentation, when needed

Keep reusable components in their own scenes when appropriate.

Do not put unrelated game systems into a single large script.

## Godot conventions

Use Godot 4 APIs and syntax.

Use:

- `snake_case` for variables and functions;
- `PascalCase` for named classes;
- clear descriptive node names;
- signals when they reduce unnecessary coupling between systems.

Prefer composition and normal Godot scene/node organization over unnecessarily
complex class hierarchies.

Do not manually modify files inside `.godot/`.
They are generated by Godot.

When manually editing `.tscn` or `.tres` files, preserve Godot's text format
carefully and validate the project afterward.

## Player

The player is a first-person 3D character.

Use `CharacterBody3D` as the basis for the player.

The initial player should support:

- WASD movement;
- mouse look;
- collision with the environment;
- configurable movement speed;
- configurable mouse sensitivity;
- releasing/capturing the mouse with an appropriate input action.

Keep horizontal body rotation separate from vertical camera rotation.

Do not add jumping, crouching, sprinting, stamina, head bob, or other movement
features unless explicitly requested.

## Flashlight

The player starts with a flashlight and always has access to it.

Use a `SpotLight3D` for the flashlight unless there is a strong technical
reason to use another approach.

Initially:

- the flashlight should be toggleable;
- it should not require batteries;
- it should not have limited energy.

Battery mechanics may be considered later but are not part of the initial
prototype.

## Environment

The initial environment should resemble a large, artificial, maze-like indoor
space.

The basic visual vocabulary is:

- yellowish walls;
- beige or brownish carpet;
- low suspended ceiling;
- fluorescent ceiling fixtures;
- repetitive and slightly incoherent architecture;
- areas that may become completely dark.

The architecture should feel more like a strangely designed building than a
traditional perfect maze.

For the initial prototype, use simple geometry. Do not require Blender assets
until they are actually useful.

## Lighting

Lighting is an important gameplay and atmospheric system.

Ceiling lights start turned off.

Lights near the player should activate as the player approaches and turn off
again after the player moves sufficiently far away.

Use different activation and deactivation distances when useful to avoid rapid
on/off switching near a distance threshold.

Ceiling lights should eventually support states such as:

- normal;
- delayed startup;
- flickering;
- permanently broken;
- permanently burned out during gameplay.

Not every light must turn on. Some areas may remain partially or completely
dark.

A light that burns out permanently during gameplay should remain burned out.

Do not simulate every distant light unnecessarily. Lighting must be designed
with large environments and performance in mind.

Avoid strong global ambient illumination. Areas without functioning lights
should be capable of becoming genuinely dark, making the player's flashlight
useful.

## Performance

The game may eventually contain a large number of rooms, walls, lights, and
repeated objects.

Keep scalability in mind, but do not prematurely optimize the prototype.

Avoid designs that require every distant object or light to execute
per-frame logic.

Prefer shared resources and reusable scenes for repeated objects.

## Development approach

Work incrementally.

For substantial features:

1. inspect the existing project first;
2. understand the current architecture;
3. propose a simple implementation;
4. make the smallest coherent change;
5. validate it;
6. report what changed and any remaining issues.

Do not rewrite working systems merely to make them different.

Do not introduce major features that were not requested.

When requirements are ambiguous, prefer the simpler implementation that is
easy to modify later.

## Validation

The `godot` executable should be available in PATH.

After changing GDScript, scenes, resources, or project configuration, validate
the project with Godot when practical.

A basic project validation command is:

    godot --headless --path . --editor --quit

Check the output for:

- GDScript parse errors;
- invalid resources;
- broken scene references;
- missing files;
- other Godot errors caused by the change.

If validation fails because of a change you made, diagnose and fix the problem
before considering the task complete.

## Git

Assume the project is version-controlled with Git.

Before substantial changes, inspect the repository state with:

    git status

Do not discard, overwrite, or revert existing user changes.

Do not make Git commits unless explicitly asked to do so.

Do not rewrite Git history.

The `.godot/` directory should not be committed.

## General principle

Keep Openrooms simple, modular, understandable, and easy to change.

The immediate objective is to build a convincing exploration prototype, not a
complete game framework.

## Development environment note

The project is currently developed inside an Oracle VirtualBox VM.

VirtualBox Mouse Integration interferes with relative mouse input used by
first-person camera control.

When testing mouse-look behavior, disable VirtualBox Mouse Integration.
Do not modify the player controller to compensate for this VM-specific issue
unless explicitly requested.
